# Admin System Audit

**Review type:** Static code and route review, with follow-up security remediation  
**Scope:** Admin page routes, privileged `/info/api/admin` route handlers, admin proxy rules, and shared admin settings/navigation code.  
**Runtime caveat:** No live administrator session or connected Supabase database was available for end-to-end verification. “Connected in code” below means a page issues the relevant database/API calls; it does not certify production behavior.

## Summary

The admin console is a mixture of database-connected workflows and UI-only mockups. The production build completes. A critical admin API authorization and user-data exposure issue found during the audit has been fixed: privileged user, tourist-spot, and forum endpoints now enforce server-side admin authorization, and the users endpoint no longer returns the password column. `/info/api/**` still passes through the proxy intentionally; privileged handlers enforce access at the route level. Unrelated gaps and mock workflows remain listed below.

Several moderation and file-management controls still only update browser `localStorage` or show success messages. The data-management page now creates admin-authorized, downloadable database snapshots and performs validated merge-only restores; automated backup scheduling, cloud archival, and media-file backup are not configured. Maintenance mode is now stored in the database and enforced by the proxy; its additive migration must be applied in each target environment. Email delivery tests use server-side SendGrid environment variables. Security controls unsupported by the auth flow have been removed rather than presented as active policies. A number of nested admin routes redirect to parent URLs that either do not exist (`/info/admin/content`) or ignore the requested `?tab=` value.

## Incomplete or misleading admin areas

- **System health and database metrics are hardcoded.** “Check Now” resets fixed values such as uptime, database size, table count, and last-backup time instead of checking services. The version/build display is also a fixed value. See `src/app/(subsystems)/info/admin/settings/page.js:9-24,97,113-114`.
- **General settings are not consistently persisted.** The general settings form writes to `localStorage`, but initializes its form state from hardcoded defaults rather than reading that stored value. Theme, rewards, and moderation preferences are also browser-local. See `src/app/(subsystems)/info/admin/settings/general/page.js:10-45,49-88`.
- **Notification templates and schedule preferences are browser-local.** Announcement categories/templates, quiet hours, digest preferences, and emergency settings are saved in `localStorage`, not a shared settings service. See `src/app/(subsystems)/info/admin/announcement-settings/page.js:17-45,67-89`.
- **Data export on the settings overview is not a dependable full export.** It iterates over tables but silently skips failed queries and still displays a success message. See `src/app/(subsystems)/info/admin/settings/page.js:61-87`.

## Validation and limits

- `npm.cmd run build`: **passed** with Next.js 16.2.10; all 101 static pages were generated.
- Targeted ESLint over admin pages, admin APIs, and shared admin components: **failed** with 2 errors and 22 warnings.
- No admin end-to-end/unit test script is defined in `package.json`; no live admin credentials or database were available for runtime checks. Database persistence, row-level policies, provider configuration, and actual user-facing behavior remain unverified.

## Recommended remediation order

1. Add automated authorization tests for anonymous, regular-user, and admin access to every `/info/api/admin/**` handler.
2. Replace local-only/mock settings, moderation, backup, import/export, and media actions with authenticated server-backed operations; remove success messages for operations that did not occur.
3. Repair admin route destinations and implement or remove the missing content and tab workflows.
4. Align user-role labels, form choices, and metrics with the database schema.
5. Rotate the previously exposed weather provider key and configure the replacement as the server-only `OPENWEATHER_API_KEY`.
6. Resolve the two lint errors, then exercise each workflow against a test database and an admin browser session.
